## 「播久了自动崩」= GPUI 精灵图集不回收（21:2x）

用户报"时间播放长了会自动崩溃，刚才崩了两次"。两条线索都没留下：
`~/Library/Logs/iPlayer/` 没有新 panic 日志，`DiagnosticReports/` 也没有新 .ips
（最新那份 `iPlayer-2026-10-09-200406.ips` 是 `SIGKILL (Code Signature Invalid)`，
即 `cp` 覆盖 app 内二进制的旧坑）→ 不是 panic，是**被系统按资源限制干掉**。

- 实测（`footprint -p <pid>`，720p《银翼杀手2049》）：`phys_footprint`
  700MB → 8514MB / 70 秒，**约 +120MB/s 线性增长**（RSS 只到 2.7GB 就平台期，
  共享模式的 Metal 纹理要 `phys_footprint` 才看得全）。
- 根因：GPUI 的 `AtlasState::tiles_by_key` 对每个没见过的 `RenderImage::id`
  分配一块 etagere tile，**只有显式 `Window::drop_image()` 才回收，没有自动 GC**。
  播放器每解一帧 `Arc::new(RenderImage::new(...))`（`player/video.rs:decode_loop`）
  → 每帧一个 id → 每帧在显存里留一块大纹理，永不释放。
- 修复（`src/app.rs`）：
  - 新增 `App.shown_frame: Option<Arc<RenderImage>>`（上一帧画到屏幕上的纹理）。
  - `render_stage` 取帧后：`needs_retire(旧 id, 新 id)` 为真 → `let _ = window.drop_image(旧)`。
    判据只看 `id`：同一帧反复取出来（暂停冻结 / 拖动停在旧画面）不白撤；画面来源
    整个消失（切图片 / 音频 / 空舞台）也要撤。撤掉的 tile 若还被上一帧场景引用，
    macOS 渲染器会跳过它（gpui-pre-apple `metal_atlas.rs` 注释里写明了）。
  - `apply_orientation` 给静态图片重算纹理时同样退旧的那张（顺带把 `window` 传进去）。
- 验证：
  - 修复后同片源 3 分钟 `phys_footprint` **135 → 143MB 水平**（旧版 70s 就到 8.5GB）。
  - 新增 `frame_retire_tests` 2 条：`needs_retire` 真值表 + 源码扫描
    （`render_stage` / `apply_orientation` 必须调 `window.drop_image(` 且由 `needs_retire` 把门）。
    临时摘掉撤帧那段确认变红，再恢复。
  - 全量 `cargo test` **114/114**；release 只有第三方 `block v0.1.6` 的 known 警告；
    `--selftest` 全绿；`bundle-macos.sh --install` 后安装版实测存活 40s、内存 138–142MB 平稳、
    无新崩溃日志、stderr 干净。

## 右键「打开方式 → iPlayer」能起应用但不播、列表为空（21:4x–22:0x）

两个叠加的根因，都修了：

1. **自己往 `NSAppleEventManager` 上挂 aevt/odoc 处理器是白搭**：AppKit 在
   `-finishLaunching` 里会给同一对 (class, id) 装它自己的处理器，把我们
   `run()` 之前抢先注册的那份**覆盖掉**，事件随后走应用委托的
   `application:openURLs:`。正解 = 接 gpui 透出来的口子
   `application.on_open_urls(native::open_urls)`（回调拿到的是
   `NSURL.absoluteString`，**百分号编码**的 file:// 字符串，用
   `NSURL::isFileURL()` + `to_file_path()` 解回路径；`URLWithString` 对
   "not-a-url" 这种相对字符串也会成功，不挡 isFileURL 会把垃圾塞进列表）。
   原来那套 AppleEventManager / NSAppleEventDescriptor 机械整个删了，
   `system_open_docs_wiring` 里钉了否定项（禁 `setEventHandler` 回潮）。
2. **帧循环是按需的，闲着的应用收不到文件**：没媒体、没面板时 `tick` 一进来
   就 return，没人再 `request_animation_frame`，队列里的文件永远没人取 ——
   "应用已经开着时右键打开方式"正是这种状态。修法 = native 入队后用
   `smol::channel` 拍一下，`App::watch_open_docs`（main.rs 开窗口时挂上的
   常驻任务）醒来 `pump_open_docs`。**不是轮询**，平时一觉睡到底。
   临时摘掉这条任务复现过回归（空闲时打开方式确实失灵），再恢复 —— 它是承重墙。

验证：`cargo test` **116/116**（新增 `system_open_docs_wiring` 源码扫描 +
`open_urls_decode_file_urls_and_ring_the_wake` 单测）、`--selftest` 全绿、
`bundle-macos.sh --install` 后用 `open -a /Applications/iPlayer.app` 实测
两个场景（冷启动 / 播完闲着）都出 ffmpeg 子进程且解的是目标文件，截图见列表有文件。
测试素材：`/tmp/iplayer-open-test.mp4`、`/tmp/iplayer-open-test2.mp4`。
