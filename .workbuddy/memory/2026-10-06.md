# 2026-10-06 — iPlayer 工作日志

## AC-3 / E-AC-3 音频不再需要转码（重大判定修正）

**背景**：`mp4 + h264 + ac3` 之前被判成 `remux`，要整片复制一遍 + 把 AC-3 重编码成 AAC，
长片要等很久。目标：找到"无需转码的解码引擎"。

**结论：不需要任何第三方引擎 —— macOS 的 WebKit 自己就带 AC-3/E-AC-3 解码器。**
WebKit 在 macOS 上走 AVFoundation 解码，AVFoundation 自带 AC-3/E-AC-3（DVD/BD 那套），
所以只要容器是 MP4/MOV，AC-3 音轨**原样 `-c copy` 就能出声**。Chromium/Firefox 不支持，
网上「浏览器不支持 AC-3」的结论对 macOS WebKit *不成立* —— 这条别被搜索结果带偏。

### 实测手法（可复用的通用手法，比在应用里注入更轻）

用 `swiftc` 编一个离屏 WKWebView 小程序（`/tmp/ac3test/main.swift`）：

- `WKWebViewConfiguration.mediaTypesRequiringUserActionForPlayback = []`
- offscreen `NSWindow` + `orderFrontRegardless()`，`load(URLRequest(http://127.0.0.1:PORT/x.html))`
- 页面里 `canPlayType` + 真播一遍，用 `AudioContext → createMediaElementSource → AnalyserNode`
  量 `getFloatTimeDomainData` 的 RMS，**RMS > 0 = 真的解码出声了，RMS = 0 = 容器认了但静音**。
- 结果经 `webkit.messageHandlers` 回主进程再 print。

**坑**：
- 测试用的 `python -m http.server` 必须和 harness 写在**同一条 bash 命令**里；
  分两次调用时后台进程会被回收，WebKit 报 `NSURLErrorCannotConnectToHost (-1004)`，
  看起来像 WebView 坏了，其实是服务没了。
- 本机 `swiftc` 可用，`NSScreen.main != nil` 有窗口服务，离屏 WKWebView 能正常跑。
- 用 `evaluateJavaScript` 拿 Promise 返回值会报 `WKErrorDomain Code=5`（不支持的类型），
  必须走 `postMessage` 回传。
- `canPlayType` 在这台机器上 **不可靠**：`avc1.64001e,aac` 返回空串但能播，
  `...,ac-3` 返回 `probably`。**只信真播一遍的 RMS**。

### 代码改动（2 个文件）

- `media.rs`：`MP4_ACODECS` 加 `ac3/eac3`；`NATIVE_ACODECS` 加 `ac3/eac3`（否则提示文案仍说"无法解码"）。
- `media.rs` 测试：matrix 里 mp4/mov + ac3/eac3 从 `remux` 改 `direct`，新增裸 `.ac3` → `remux`、
  `mkv+ac3` → `remux`、`mkv+dts` → `remux`；`audio_container_fit` 与 `reasons` 同步更新
  （`reasons` 的 AC-3 用例改成 DTS，另加 m2ts+ac3「只解释容器、不提音频」的断言）。
- `commands.rs`：只是注释更新（`run_remux` 本来就会按 `audio_fits` 决定 `-c a copy`，无需改逻辑）。
- **DTS 保持不变**：WebKit 会接受容器然后播静音，所以 DTS 继续走音频重编码。

### 收益（3 分钟 1080p / 181 MB，MKV + AC-3，暖缓存）

- 旧：`-c:v copy -c:a aac` → **1.81 s**
- 新：`-c copy` → **0.17 s**（约 10×，音轨原样保留 AC-3 6ch）
- `mp4 + ac3` 原文件：**plan=direct，完全不生成副本**（耗时 0）

## `npm run build` 报 `tauri: command not found`（已修）

**根因**：`node_modules/` 根本不存在，依赖从来没装过。`npm run build` → `tauri build`，
而 `tauri` 是从 `node_modules/.bin/` 解析的，目录不存在就报 command not found。
（不是 PATH 问题，也不用全局装 CLI。）

**修法**：`npm install`（只有 2 个包，`@tauri-apps/cli` + `cli-darwin-arm64`，6 秒）。
`package-lock.json` 本来就和依赖一致，装完没有改动。

### sidecar：一个会毁数据的坑（重要，勿重犯）

构建前必须有 `src-tauri/binaries/{ffmpeg,ffprobe}-<triple>`，否则 `tauri build`
直接失败：`resource path binaries/ffmpeg-aarch64-apple-darwin doesn't exist`。

**坑**：`scripts/fetch-sidecar.mjs` 用 `writeFileSync(dest, buf)` 写目标路径。
如果 `dest` 是**软链**（例如之前有人把它链到 `/opt/homebrew/bin/ffmpeg`），
`writeFileSync` 会**顺着软链写穿**，把 Homebrew 的 ffmpeg 覆盖成下载下来的另一个文件。
→ **跑 `fetch:sidecar` 之前必须先 `find src-tauri/binaries -type l -delete`**。

### 本机网络的实际情况

- `curl -I https://github.com/...` → 302（通）；但**真正下载 release 资源** `http=000`、curl exit 56
  （10s 断流）→ `eugeneware/ffmpeg-static` 的 4 个静态包全部 `fetch failed`。
- `registry.npmjs.org` 通（`npm install` 正常）。
- 所以 `fetch:sidecar` 走了 fallback：从 PATH 拷本机 Homebrew ffmpeg/ffprobe 到 `src-tauri/binaries/`。
  拷出来的是**真实文件**（不是软链），`otool -L` 显示它动态链接
  `/opt/homebrew/Cellar/ffmpeg/9.0.2/lib/*.dylib`（**36 个外部 dylib，含 ffmpeg 自身那一坨**）。
  → **本机能跑，换台机器就废**。要做可分发的包，三选一：
  1. 换有 GitHub 访问的网络跑 `npm run fetch:sidecar`（最省事，脚本本来就是为这个写的）；
  2. 用 npm 上**二进制打在 tarball 里**的包：`@ffmpeg-installer/darwin-arm64`
     （unpacked 36.7MB，装包即得，不依赖 GitHub；但版本只有 4.1.5，2019 年的，偏老）；
  3. 用 `dylibbundler` 把那 36 个 dylib 拷进 `Contents/Frameworks` 并 `install_name_tool` 改路径
     （完全离线，能保住 ffmpeg 9.0.2，但要改 tauri build 流程）。
