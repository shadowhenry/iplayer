### 这次真正抓到的问题（都是靠"临时 trace 文件"发现的）
1. **帧循环只转 3 帧就停**。表象是"打开视频后界面卡在起播"。链路是：
   `VideoTrack::advance()` 把 `try_recv` 的 `Err(_)` 一律当 drain → 起播瞬间通道必然空 →
   `drained = true`；同时 `ended()` 里 `current_pts` 还是 `-1`，于是 `position >= -1 - 0.5` 恒真 →
   第一帧就被判"播完" → `tick()` 走 `LoopMode::Off` 且 `current` 是 None → `p.pause()` →
   `playing = false` → 不再 `request_animation_frame()`。
   修：`advance()` 区分 `TryRecvError::{Closed, Empty}`（只有 Closed 才 drained）；
   `ended()` 加 `current_pts >= 0.0` 前置条件。
2. **暂停中 seek 后画面全空**。`spawn()` 会把 `current` 清掉，而 `frame()` 在非播放态直接返回缓存。
   修：非播放态仅在 `current.is_some()` 时冻结，否则允许 `advance()` 挑一次（靠 app 侧 `warmup` 重试）。
   顺手给 `--selftest` 加了这条断言的回归检查。
3. `App::open_file` 直接打开单个文件时没有在 `view` 里定位，`self.current` 恒为 None →
   "播完接下一集"失效。修：进 `open_file` 就先按路径回查 `view`。

### GPUI 的坑（详见 MEMORY.md）
`cx.notify()` 不驱动帧源；`WindowOptions::default()` 帧循环不转；Rust 2024 下 render 辅助方法要
`-> impl IntoElement + use<>`；`bool::then(|| self.render_x(cx))` 会拖长借用；`SliderState` 没有
`max` setter（改用 0–1 归一化）；`set_value` 要一个用不到的 `&mut Window`（`update_in` 要
`VisualContext`，`Context<T>` 不满足，所以用 `update`）；`RenderImage` 是 BGRA。
`gpui_kit::actions::ToggleSidebar` 和 `cx.window_handle_placeholder()` **都不存在**（早期草稿猜的）。

## 修「播放进度条不支持拖动」

用户报的。**根因不在事件绑定，在 SliderState 的 `step` 默认值**：进度条按 0–1 归一化
（`min`/`max` 只能在构造时设，记忆里早记过），而 `step` 默认 `1.0`，指针交互算的是
`(value / step).round() * step` → 每次都被吸附到 **0 或 1**。所以点哪儿都跳两端、拖不动。
音量条是 0–100、步长 1 正好，所以它一直正常 —— 这也是我能迅速缩小范围的关键对照。
修法：`SliderState::new().min(0.).max(1.).step(0.0001)`。

### 怎么找到的：给 GPUI 加无头指针测试

- Cargo 加 `[dev-dependencies] gpui = { package = "gpui-pre", version = "=0.3.8", features = ["test-support"] }`
  （与 gpui-kit 依赖同一个包，特性合并、类型同一）。
- 元素加 `.debug_selector(|| "seek-row".into())`，测试里 `cx.debug_bounds("seek-row")` 拿坐标，
  再 `simulate_mouse_move/down/up` 打真实指针事件。
- 踩的坑：① 按下前必须先发一次**无按键** move，否则 `hitbox.is_hovered()` 为假、拖拽不启动；
  ② GPUI 越过 `DRAG_THRESHOLD` 才建立拖拽，且**建立那次 move 不派发 drag_move**，要连发几次；
  ③ 不要在 down 和 move 之间插 `cx.update`（多画一帧会丢 `pending_mouse_down`）。
- 反向验证：把 `.step()` 去掉后测试报「拖到 75% 实际 1」（正是"跳到底"的症状），加回来变 0.75。

### 结果

- `cargo test` **24/24**（新增两条：`seek_slider_can_be_dragged` + 对照 `volume_slider_can_be_dragged`）。
- 重新打包 `dist/iPlayer.app`（103M）并冒烟：存活。

```css
.ctrl-group.center { justify-self: end; }        /* 播放组贴着音量组，两个一起靠右 */
#app.sidebar-hidden .ctrl-row { grid-template-columns: 1fr auto 1fr; gap: 14px; }
#app.sidebar-hidden .ctrl-group.center { justify-self: center; }     /* 回到整行正中 */
```

GPUI 版把中间那格写成 `flex_1 + justify_center`，于是播放组永远停在「时间」和右侧控制组
**之间那段空隙**的中央 —— 因为右侧那坨比左侧时间宽得多，它的视觉中心被推到了音量条旁边，
既不是整行正中，也不会随侧栏变。这就是用户看到的症状。

### 改法（`render_controls`）

- 把右组（音量/倍速/循环/信息/截图）先单独造成一个 `right`，再决定槽宽：
  ```
  let slot = div().flex().items_center().justify_end();
  let slot = if sidebar_open { slot } else { slot.flex_1().min_w(px(0.)) };
  ```
  展开 → 右组是 `auto` 宽、直接贴右，播放组就挨着它；
  收起 → 右组套一个和左边等宽的 `1fr`，两边一配对，播放组自然落在整行正中。
- 左「时间」格改成 `flex_1`（展开时它吃掉全部余量，把后两组挤到右端）；
  中间播放组去掉 `flex_1`，改成 `flex_none`。
- 行间距照抄原版：展开 8px、收起 14px。两个 `1fr` 之间各一个等宽 gap，不影响居中。

### 测试（`mod control_bar_tests`）

给行/播放组/右组分别挂 `ctrl-row` / `play-group` / `vol-cluster` 选择器，用 `debug_bounds` 量几何：

- 展开：播放组中心落在整行 **82%** 处，右缘到音量组 **8.0px**（正好一个行间距 = 贴着）。
- 收起：播放组中心 = 行中心 = 960（行宽 1920），**偏离 0.0px**；到音量组 620px 远。

**踩坑**：`Pixels` 的字段是私有的，`.0` 取不出来，得 `f32::from(p)`。

**反向验证**：把 `if sidebar_open` 钉成 `true` → 收起态那条挂（播放组不居中）；
钉成 `false` → 展开态那条挂（播放组被居中，不再贴音量）。两态各自被卡住。
