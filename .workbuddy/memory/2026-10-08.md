### 这次真正抓到的问题（都是靠"临时 trace 文件"发现的）
1. **帧循环只转 3 帧就停**。表象是"打开视频后界面卡在起播"。链路是：
   `VideoTrack::advance()` 把 `try_recv` 的 `Err(_)` 一律当 drain → 起播瞬间通道必然空 →
   `drained = true`；同时 `ended()` 里 `current_pts` 还是 `-1`，于是 `position >= -1 - 0.5` 恒真 →
   第一帧就被判"播完" → `tick()` 走 `LoopMode::Off` 且 `current` 是 None → `p.pause()` →
   `playing = false` → 不再 `request_animation_frame()`。
   修：`advance()` 区分 `TryRecvError::{Closed, Empty}`（只有 Closed 才 drained）；
   `ended()` 加 `current_pts >= 0.0` 前置条件。
2. **暂停中 seek 后画面全空**。`spawn()` 会把 `current` 清掉，而 `frame()` 在非播放态直接返回缓存。
   修：非播放态仅在 `current.is_some()` 时冻结，否则允许 `advance()` 挑一次（靠 app 侧 `warmup` 重试）。
   顺手给 `--selftest` 加了这条断言的回归检查。
3. `App::open_file` 直接打开单个文件时没有在 `view` 里定位，`self.current` 恒为 None →
   "播完接下一集"失效。修：进 `open_file` 就先按路径回查 `view`。

### GPUI 的坑（详见 MEMORY.md）
`cx.notify()` 不驱动帧源；`WindowOptions::default()` 帧循环不转；Rust 2024 下 render 辅助方法要
`-> impl IntoElement + use<>`；`bool::then(|| self.render_x(cx))` 会拖长借用；`SliderState` 没有
`max` setter（改用 0–1 归一化）；`set_value` 要一个用不到的 `&mut Window`（`update_in` 要
`VisualContext`，`Context<T>` 不满足，所以用 `update`）；`RenderImage` 是 BGRA。
`gpui_kit::actions::ToggleSidebar` 和 `cx.window_handle_placeholder()` **都不存在**（早期草稿猜的）。

## 修「播放进度条不支持拖动」

用户报的。**根因不在事件绑定，在 SliderState 的 `step` 默认值**：进度条按 0–1 归一化
（`min`/`max` 只能在构造时设，记忆里早记过），而 `step` 默认 `1.0`，指针交互算的是
`(value / step).round() * step` → 每次都被吸附到 **0 或 1**。所以点哪儿都跳两端、拖不动。
音量条是 0–100、步长 1 正好，所以它一直正常 —— 这也是我能迅速缩小范围的关键对照。
修法：`SliderState::new().min(0.).max(1.).step(0.0001)`。

### 怎么找到的：给 GPUI 加无头指针测试

- Cargo 加 `[dev-dependencies] gpui = { package = "gpui-pre", version = "=0.3.8", features = ["test-support"] }`
  （与 gpui-kit 依赖同一个包，特性合并、类型同一）。
- 元素加 `.debug_selector(|| "seek-row".into())`，测试里 `cx.debug_bounds("seek-row")` 拿坐标，
  再 `simulate_mouse_move/down/up` 打真实指针事件。
- 踩的坑：① 按下前必须先发一次**无按键** move，否则 `hitbox.is_hovered()` 为假、拖拽不启动；
  ② GPUI 越过 `DRAG_THRESHOLD` 才建立拖拽，且**建立那次 move 不派发 drag_move**，要连发几次；
  ③ 不要在 down 和 move 之间插 `cx.update`（多画一帧会丢 `pending_mouse_down`）。
- 反向验证：把 `.step()` 去掉后测试报「拖到 75% 实际 1」（正是"跳到底"的症状），加回来变 0.75。

### 结果

- `cargo test` **24/24**（新增两条：`seek_slider_can_be_dragged` + 对照 `volume_slider_can_be_dragged`）。
- 重新打包 `dist/iPlayer.app`（103M）并冒烟：存活。

```css
.ctrl-group.center { justify-self: end; }        /* 播放组贴着音量组，两个一起靠右 */
#app.sidebar-hidden .ctrl-row { grid-template-columns: 1fr auto 1fr; gap: 14px; }
#app.sidebar-hidden .ctrl-group.center { justify-self: center; }     /* 回到整行正中 */
```

GPUI 版把中间那格写成 `flex_1 + justify_center`，于是播放组永远停在「时间」和右侧控制组
**之间那段空隙**的中央 —— 因为右侧那坨比左侧时间宽得多，它的视觉中心被推到了音量条旁边，
既不是整行正中，也不会随侧栏变。这就是用户看到的症状。

### 改法（`render_controls`）

- 把右组（音量/倍速/循环/信息/截图）先单独造成一个 `right`，再决定槽宽：
  ```
  let slot = div().flex().items_center().justify_end();
  let slot = if sidebar_open { slot } else { slot.flex_1().min_w(px(0.)) };
  ```
  展开 → 右组是 `auto` 宽、直接贴右，播放组就挨着它；
  收起 → 右组套一个和左边等宽的 `1fr`，两边一配对，播放组自然落在整行正中。
- 左「时间」格改成 `flex_1`（展开时它吃掉全部余量，把后两组挤到右端）；
  中间播放组去掉 `flex_1`，改成 `flex_none`。
- 行间距照抄原版：展开 8px、收起 14px。两个 `1fr` 之间各一个等宽 gap，不影响居中。

### 测试（`mod control_bar_tests`）

给行/播放组/右组分别挂 `ctrl-row` / `play-group` / `vol-cluster` 选择器，用 `debug_bounds` 量几何：

- 展开：播放组中心落在整行 **82%** 处，右缘到音量组 **8.0px**（正好一个行间距 = 贴着）。
- 收起：播放组中心 = 行中心 = 960（行宽 1920），**偏离 0.0px**；到音量组 620px 远。

**踩坑**：`Pixels` 的字段是私有的，`.0` 取不出来，得 `f32::from(p)`。

**反向验证**：把 `if sidebar_open` 钉成 `true` → 收起态那条挂（播放组不居中）；
钉成 `false` → 展开态那条挂（播放组被居中，不再贴音量）。两态各自被卡住。

### 右上角新增"画面角度"（左/右转 90°、左右/上下翻转、复位）
用户原话："右上角增加一个调整画面角度的操作，左右翻转，上下翻转，右转90度，左转90度等"。

**数据模型（`player/video.rs::Orientation`）**
- 字段 `rot: u32`（0/90/180/270，顺时针）+ `flip_h` + `flip_v`。
- **语义 = 屏幕空间**：`rot` 是把"屏幕上看到的那张图"顺时针转过的角度，翻转作用在转完
  之后。所以 `flipped_h()` 必须把已有旋转换算成 `rot = (360 - rot) % 360`
  （`水平翻转 ∘ 旋转 θ = 旋转 −θ ∘ 水平翻转`），否则转 90° 后再点"左右翻转"会变成上下翻。
- `(rot,h,v)` 有 16 种写法但只有 8 种效果（`上下翻转 = 左右翻转 ∘ 旋转 180°`），
  所以有 `canonical()` / `same_effect()`；`set_orientation` 用它做 early-return，
  免得等价写法白重开一次解码让画面闪。
- `filter_tail()` → ffmpeg：90 = `,transpose=1`、270 = `,transpose=2`、180 = `,hflip,vflip`，
  翻转再追加 `,hflip`/`,vflip`；`dims()` 在 90/270 时宽高互换。
  `map_back(ox,oy,w,h)` 是同一套语义的逆向映射，给静态图片的 CPU 变换用。

**视频**：`build_command` 把 `filter_tail` 接在 `scale=w:h` **之后**（先缩好再转，
输出尺寸才确定）；`spawn` 里按 `orient.dims(out_w,out_h)` 决定真正读多少字节。
换角度 = `VideoTrack::set_orientation` → `spawn(当前位置)`，**跟 seek 同一条路径**
（重开 ffmpeg 子进程、时间戳归零），音频和 timeline 完全不动。

**静态图片**：没有解码进程可挂，走 `player::orient_image`（CPU 倒一遍像素，
`RenderImage` 的 BGRA 缓冲直接搬）。App 里额外存一份 `still_base`（未变换的原图），
每次调角度都从它重算，不在转过的图上再转。

**UI**：右上角图标区顺序 = 置顶 / **画面角度** / 导出工具箱 / 全屏。面板是舞台里的
右上角浮层（和右下角的导出面板互斥），菜单项 左转 90° / 右转 90° / 左右翻转 /
上下翻转 / 恢复原始，标题里带当前朝向（`Orientation::label()`）。换文件时朝向复位
（`open_file` 开头），因为手调角度是"针对这一部片"的。图标 `icons.rs::"rotate"`
是**逆时针**环形箭头（`refresh` 是顺时针那只，别混）。

**这次的坑（重要）**

## 23:5x 点"截图 / 转 GIF"崩溃 —— 真凶是**同步保存面板的嵌套 run loop**

**现象**：点截图（上一轮）和点"转 GIF"（本轮）都直接崩，`~/Library/Logs/iPlayer/`
里只有一句 `panic in a function that cannot unwind`。上一轮把"在 click 回调里弹
对话框"改成"下一帧在帧回调里弹"**完全没用** —— 因为帧回调本身也在同一条
extern "C" 回调链里。

**根因（这次定到了）**：`rfd::FileDialog::save_file()` 是同步版，内部
`NSPanel.runModal`，会在主线程上**再叠一层事件循环**。而 GPUI 的帧源恰好是
一块挂在**主队列**上的 dispatch source（`gpui-pre-macos/src/display_link.rs`：
`DispatchSource::new(&_dispatch_source_type_data_add, 0, 0, Some(DispatchQueue::main()))`），
模态期间照样触发 → 帧回调**重入** GPUI（app 状态被重复借用）→ panic；
偏偏这个回调站在 `extern "C"` 边界上没法 unwind → 直接 abort。

**修法**：改用 rfd 的**异步**版 `AsyncFileDialog::save_file()`，底层是
`beginSheetModalForWindow:completionHandler:` —— 挂在窗口上的 **sheet，不阻塞**，
没有嵌套事件循环。
- 新增 `PendingSave { kind, src, pos, dur, fut }` + `App::dialog`；tick 里用
  `std::task::Waker::noop()` 每帧轮询 `PendingSave::poll()`
  （`None`=面板还开着 / `Some(None)`=取消 / `Some(Some(p))`=选了 p）。
- **必须 `.set_parent(&*window)`**（`Window` 已实现 `HasWindowHandle+HasDisplayHandle`）：
  rfd 找不到父窗口时会自动退回同步 `runModal`，那条老路照样崩。
- 原 `start_export` 拆成 `request_export`（校验 + 弹非阻塞面板）+ `begin_export`
  （起 ffmpeg 任务）；`pending_export` 字段整个删掉。

**验证手法（沙箱里 GUI 只能这么测）**：临时探针在 tick 第 40 帧触发
`request_export`，第 300 帧用 `NSApp.keyWindow()` + `endSheet_returnCode(0)` 关掉 sheet。
结果：`request_export` 立即返回（dialog=true）、帧循环照常推进（tick 60→240→300，
**没有嵌套模态**）、关掉后 dialog 立刻变 false 且进程不崩；
配合"跳过面板直接 begin_export"跑通三种产物（PNG 320x240 / M4A AAC / GIF 480x360）。

**教训**：这个环境里，**任何会自己开事件循环的同步 API 都不能在主线程调**
（rfd 同步对话框、`runModal` 一类）；GPUI 的帧源在主队列上，模态期间不会停。

**顺带**：panic 钩子的文件名原来只精确到秒，而一次 abort 会调用钩子两遍
（原始 panic + "cannot unwind"），同名互相覆盖会把最要紧的第一条消息冲掉 ——
已改成 `crash-<毫秒>-<序号>.log`。

**测试**：66/66（新增 `export_dialog_tests` 三条：poll 非阻塞 / 交出路径 / 区分取消）。

## 22:3x~23:5x 「点截图/转 GIF/提取音频就崩」——真凶找到并修掉

用户连报三次（截图 → 转 GIF → 提取音频），前两次的"修法"都没中。这次挖到了根：

**根因（rfd 0.15.4 静默退回同步 `runModal`）**
`rfd::AsyncFileDialog` **不保证**走 sheet。`backend/macos/modal_future.rs:79` 的
判断是 `NSApp.isRunning() && win.is_some()`，任一不满足就打印
"I will fallback to sync dialog for you" 然后**当场同步 `inner.run_modal()`**
（第 105~115 行）。`runModal` = 在主线程里再叠一层事件循环，
而 GPUI 的帧源/事件分发都在这条链上 → 嵌套循环里一有事件（转发的鼠标抬起、
display link 帧回调）就重入 GPUI → panic → 撞 ObjC 边界无法 unwind → abort。
所以前两版"改异步 API""延到下一帧弹"都白改：**只要 rfd 走了回退，就是同一个坑**。
（23:21 那两份 .ips 的 `_routeLeftMouseUpEvent` 栈就是这么来的：嵌套 runModal 把
用户那记鼠标抬起转给了 GPUI，而外层分发还没退出。）

**修法**
1. `native::async_sheet_available(window)`：先自查 `ns_window()` 拿得到 +
   `NSApplication.isRunning()`，不满足就**干脆不开面板**（给 toast），
   绝不让 rfd 掉进同步回退。实测真实 app 里返回 `true`（面板照常弹）。
2. `request_export` 里把 `AsyncFileDialog…save_file()` 包进
   `catch_unwind(AssertUnwindSafe)`，万一 rfd 自己 panic 也只是一句 toast
   + `panic_reason()` 提取消息，不再带走进程。
3. **panic 钩子不能再 panic**：`eprintln!` 在 stderr 断管时会自己 panic，
   而此时已在 panic 中 → 标准库直接 abort，**原始消息全丢**（23:30 那份
   `iplayer-2026-10-08-233050.ips` 就是我的 `--selftest | grep` 触发的 SIGPIPE，
   栈顶 `__print → orientation_selftest`）。改成：先写文件、再 `let _ = writeln!(stderr)`、
   不调 `default_hook`。
4. `Cargo.toml`: `strip = true` → `strip = "debuginfo"`，**只剥 DWARF 留符号表**
   （15MB → 22MB），以后 .ips / backtrace 直接出函数名，不用再对着十六进制偏移猜。

**怎么复现/验证的（这招可复用）**
无头 `#[gpui::test]` 里直接 `simulate_click("shot")` —— rfd 在无头环境必然走回退，
于是**在测试里就能看到那句 panic**：
`rfd-0.15.4/src/backend/macos/modal_future.rs:117: Fallback Sync Dialog Must Be
Spawned On Main Thread`。修完这条测试变成"点击只给提示、进程照常"。
真实 app 侧用临时探针复核：`async_sheet_available=true` → `request_export` 立即返回
(dialog=true) → tick 20/60/120/.../300 一直在转（**无嵌套模态**）→ `endSheet_returnCode(0)`
后 dialog=false、无 panic、日志里没有 "unsupported environment"。

**测试**：68/68（新增 `export_click_tests`：点击不崩 + 给提示、`panic_reason` 载荷解析）。
release 0 警告、selftest 三项 ✓、GUI 冒烟存活、已重打包 dist/iPlayer.app (108M)。

## 2026-10-08 23:55 · 拖进度条黑屏/屏闪（真凶：seek 把 current 清成 None）

**现象**：拖动播放条时画面黑一下再亮一下、一直闪。

**根因**（两处叠加，都在我自己的代码里）：
1. `VideoTrack::spawn()`（seek / 换角度共用）里有一句 `self.current = None`。
   于是**每一次 seek 都必定丢掉当前画面**，直到新 ffmpeg 进程起好、定位、解出第一帧
   （实测中位 24ms，1080p 更久）—— 这段空窗期 `render_stage` 落到
   `Stage::Empty if player.is_some()` 分支，显示"正在起播…"叠在黑底上。
   拖一次黑一下，拖 N 次黑 N 下。
2. `Player::frame()` 的暂停冻结条件只看了 `!playing && current.is_some()`，
   所以"暂停 + 拖进度条"时新画面永远上不来（`advance` 根本不被调用）——
   去掉 1 之后如果不动这里，就变成"画面卡在旧位置不动"。

**修法**：
- `spawn()` **不再清 `current`**：旧画面留在屏上，新帧到了自然被替换（连
  换角度也顺带不闪了）。但 `current_pts` 必须归 `-1`，否则往回拖时新帧 pts 比旧的小，
  会被 `set_current` 的单调性 `f.pts >= self.current_pts` 挡掉 → 画面卡死。
- 新增 `awaiting`（等本轮重开的第一帧）+ `empty_spawn`（本轮一帧没上屏就 EOF）：
  - `frame()` 改成 `freeze_current(playing, has_current, awaiting)`（抽成自由函数，
    配真值表单测），"等新帧"时即使暂停也允许挑帧；
  - `awaiting()` 让 `App::tick` 的 `busy` 把它算进去 —— 否则暂停拖条时帧循环停了，
    新画面出来也没人画。
  - `empty_spawn` 顺带修掉"拖到最右边（定位到末尾之外）→ `current_pts` 永远 -1 →
    `ended()` 永远 false → 一直僵在播放中"的老毛病。
- **拖动只重开视频**：新增 `Player::scrub()`（不动音频解码进程），`Change` 事件走
  `scrub_to_ratio`，`Release` 才走完整 `seek_to_ratio`。以前拖一次要起停
  2 个 ffmpeg（视频 + 音频），声音会碎、调度也更挤。

**验证（可复用手法）**：
- `--selftest` 里加"模拟拖动 2 秒"（20 次 seek，每 100ms 一次，像帧循环一样每 2ms 取一次帧）：
  结果 **黑屏采样 0 / 呈现过 91 帧 / 预览 seek 出帧延迟中位 24ms、最慢 30ms**
  （节流 90ms 是配平的，没出现"进程还没出帧就被掐掉"）。
- `cargo test` 加 `player::tests::scrub_keeps_the_old_frame_until_the_new_one_arrives`：
  用内置 ffmpeg 现造 4s 无声短片，钉死"seek 瞬间旧画面还在"+"随后必须换新帧"+"往回拖也要更新"。
  **临时把旧行为（`current = None`）放回去跑，这条用例确实红**
  （`left: None / right: Some(0)`）—— 钉子是真的。
- 测试 69 → 70/70、release 0 警告、selftest 全绿、GUI 冒烟存活、
  已重打包 `dist/iPlayer.app` (108M)。

**遗留（没做，用户没提）**：拖动节流还是固定 90ms。4K/HEVC 大片源上单次预览 seek
可能超过 90ms，那时每个进程都会被下一次 seek 掐掉，画面看着是"卡住"（不是黑屏）。
`--selftest` 已经把中位/最慢延迟打出来了，如果真遇到，按实测值自适应即可。
