# 2026-10-04

## 播放判定改为「容器感知」，把可直出的 MP4 全部从转码里救回来

用户反馈：有些 MP4 仍要转码，"不能全部支持吗"。

### 结论（能力边界）
WebKit 的解码器是固定的，以下**必须**重新编码，无解：
MPEG-4 Part 2 / DivX / Xvid（`mpeg4`）、MPEG-2、VC-1/WMV、10-bit H.264（Hi10P）、
4:4:4 / 4:2:2 色度、以及不支持 AV1 硬解的机器上的 AV1。

以下**不需要**重编码，属于之前判定的浪费，已修：
1. HEVC 标签 `hev1` → 只需 `-c copy -tag:v hvc1`（实测 hvcC 参数集完整保留，2.4KB/4 arrays）。
2. 仅音轨不被支持（MP4/MOV 里的 AC-3 / E-AC-3 / DTS / Opus / FLAC）→ 画面拷贝，只重编码音轨。
3. VP9/AV1 装在 MP4 里、H.264/HEVC 装在 WebM 里 → 换容器即可（旧逻辑误判 direct）。

  / `remux_target_container()` / `explain_plan()`。`needs_hvc1_tag()` 已删除。

## 追问「avi / flv / wmv 等格式是否支持」→ 查出一个 AVI 真 bug 并修掉

造了 8 个样本（avi_h264_mp3 / avi_h264_pcm / avi_divx_mp3 / avi_mjpeg / flv_h264 / flv_sorenson / wmv2 / msmpeg4v2）逐一走**应用同一套参数**的派生命令。

- **发现**：AVI + H.264（有 B 帧）`-c copy` 到 mp4 后，`ffmpeg -f null -` 报 `non monotonically increasing dts`。
  根因是 AVI 容器只存一个采样时间戳、**没有 PTS**（`ffprobe` 里 pts_time 全是 N/A），ffmpeg 读 AVI 时只能拿 DTS 当 PTS，
  有 B 帧时帧序就错了。试过 `-fflags +genpts`、`-avoid_negative_ts make_zero`、`-copyts`、`-fps_mode cfr`，**全部无效**（信息本来就不在容器里）。
  注意 `has_b_frames` 从 ffprobe 拿得到（AVI+h264 → 2，mpeg4/mjpeg → 0），是可靠判据。
- **修法**：新增 `container_lacks_pts(ext)`（avi/divx）+ `needs_reencode_video()`，
  `container_lacks_pts && has_b_frames > 0` → 必须 transcode；FLV 能存 CTS，不受影响（flv_h264 拷贝 0 告警）。
- **重构**：`plan_for` / `explain_plan` 的 7 个位置参数改为 `StreamTraits` 结构体（新增 `has_b_frames`），
  `MediaInfo` 同步加字段；测试改用 `t(...)` 辅助函数。
- **顺带**：`NATIVE_CONTAINERS` 补入 3gp/3g2/f4v（整个 ISO-BMFF 家族），这类 h264 文件现在**直接播放**，不再白转一次封装。
- 判定矩阵测试扩到 60+ 例（含 avi 有/无 B 帧、flv、wmv、ts/mpg/vob/dv/ogv/amv/mxf/rm、3gp 系列）。
- 真实文件经 `probe()` 全链路验证（临时 `tmp_e2e` 测试读完即删）：7 个样本的 plan 与 plan_reason 均符合预期。
- 最终 `npm run build` 通过。

## 追问「wmv / flv / mpeg 还需要转码播放」→ 实测确认边界，并给转码进度补上原因与预计剩余

造了 9 个样本（flv_h264_aac / flv_h264_mp3 / flv_flv1_mp3 / wmv2 / msmpeg4v2 / mpeg1.mpg / mpeg2.mpg / mpeg2.vob / ts_h264.ts）
跑 `probe()` 全链路 + 按应用同一套参数生成派生文件复核。

### 实测结论（回答用户就按这个说）
- **FLV 要看里面装什么**：H.264（+aac/mp3，含 B 帧）→ `remux`，只换容器不动画面；
  老式 Sorenson Spark（`flv1`）/ VP6 → `transcode`。**不存在"FLV 一律转码"这回事。**
- **WMV / ASF**：`wmv1/wmv2/wmv3`、`vc1`、`msmpeg4*` 一律 `transcode`（内核没有任何这些解码器）。
- **MPEG(.mpg/.mpeg/.vob)**：`mpeg1video`/`mpeg2video` 一律 `transcode`。容器里若是 h264，仍是 `remux`。
- 所有派生产物 `ffmpeg -f null -` 解码无错，`probe()` 复核全部落在 `direct`。

### 顺带测掉的三个性能假设（**都别再试了**）
- `h264_videotoolbox` 硬件编码**并不比 libx264 veryfast 快**（1080p 20s：7.10s vs 7.54s），
  因为在噪声/真实影片内容下**瓶颈是解码**（wmv2 1080p 软解 ≈ 3x 实时），编码不是瓶颈 → 换编码器无收益。
- `-hwaccel videotoolbox` 对 mpeg2 **没有解码器**（`Failed setup for format videotoolbox_vld`）；
  但 mpeg2 软解很快（1080p ≈ 54x 实时），wmv2 软解慢（噪声内容 ≈ 3x 实时、干净内容 ≈ 18x 实时）。
- 真正让"要等很久"的值钱方向只有**边转码边播放**（MSE 喂 fMP4 + 跳转处重开转码），尚未实现。

  让 busy 覆盖层一开始就有"为什么在转换"（需要 `tauri::Emitter`）。

  传 note 时必须每次都带，否则会被下一次进度事件清掉。**

## 边转码边播放（MSE 喂 fMP4）—— "死结"格式现在打开即播

用户："顺手改掉"。目标：WMV / MPEG / DivX / Hi10P 这类必须重编码的，不要等整段转码，打开几秒内能看，
拖进度条也不等；**且不写磁盘临时文件**。

### 架构
- `src-tauri/src/stream.rs`（新）：会话管理 + 管道背压。
  - ffmpeg 输出 `-movflags +frag_keyframe+empty_moov+default_base_moof+negative_cts_offsets -f mp4 pipe:1`
    → `ftyp + moov + (moof + mdat)*`，moov 先写完，可流式喂 MSE（不需要 moov 在文件头）。另加 `-frag_duration 2000000`。
  - `-ss <start>` 放 `-i` 前（源内定位）；实测**输出时间戳一律归零**（与源容器无关）→
    定位到别处必须由前端 `timestampOffset` 承担，别指望 ffmpeg 带偏移。
  - 读线程 `pump_pipe`：读满 64 KiB 即 `sync_channel(16).send`，通道满则阻塞 → 反压到 ffmpeg（≈1 MiB 缓冲），
    编码器被播放节奏节流，不会跑飞。
  - `GOP_SECONDS = 2.0`，`gop = clamp(round(fps*2), 12, 400)`（适配 12/25/60 fps）；
    `-preset veryfast -crf 23 -g gop -keyint_min gop -sc_threshold 0 -pix_fmt yuv420p`，音频 `aac 192k ac 2`。
  - 命令：`stream_start / stream_read / stream_status / stream_stop`；`stream_read` 返回
    `tauri::ipc::Response::new(Vec<u8>)` → JS 侧直接拿 `ArrayBuffer`（原始字节 IPC，不 base64）。
  - `lib.rs`：`RunEvent::Exit → stream::kill_all()` 防 ffmpeg 孤儿；`reap_finished()` 在每次 start 时回收。
- `src/stream.js`（新）：MSE 喂流器。
  - 前端手工解顶层 box，**只 append 完整 box**（半个 fragment 会 appendBuffer 报错）。
    `completeEnd(bytes)` 找最后一个完整 box 结尾；`endAfterBox(bytes,"moov")` 切初始化段。
  - MIME **从数据推断**：读 `avcC` 的 profile/compat/level → `avc1.PPCCLL`（不猜 profile），有 `mp4a` 再拼 `mp4a.40.2`。
  - 常量：`PULL=262144, AHEAD=30, MAX_BUFFERED=180, RESTART_GAP=12, IDLE=200, PRIME=0.35, OPEN_TIMEOUT=25000`。
  - `begin()` 起播；`requestRestart(t)`（300ms 去抖，返回 fresh 供去重 OSD）→ `doRestart(t)` 重开编码器；
    `stop()` 做 `gen++` / `stream_stop` / revokeObjectURL。所有异步循环用 `my===gen` 判失效。

### 踩过的坑（关键，勿回退）
1. **`ms.duration` 不设 → seek 被钳在 buffered 范围**。第一次自测 `SEEK -> 96.0` 但 `currentTime` 只到 39。
   修：`ms.duration = duration + 1`。修后 `seekable=[0.0-121.1]` 正常。
2. **跳转后播放头停在 gap 起点**：`bufferEnd()`（全局最远）会误判"缓冲充足"而停止拉取。
   修：新增 `bufferAhead()` = 播放头**所在区间**末端，`pump` 用它判断；`doRestart` 结束时校正 `video.currentTime = offset`。
3. **程序自身设 currentTime 会触发 `seeking`**，把播放头拉到最远 buffered 造成视觉回跳。
   修：`restarting` 守卫 + 暴露 `Streamer.repositioning()`，`seeking` 监听里 `if (Streamer.repositioning()) return;`。
4. 拖动中重复请求重启 → `requestRestart` 返回 `fresh` 布尔决定是否 `osd()`，避免刷屏。
5. `completeEnd` 里遗留的 `if (i > 8MiB && i === bytes.length) break;` 会漏掉后续 box，已删。
6. `-ss` 归一化时间戳曾让我误判"定位没生效"（用 `-copyts`/`setpts` 都测出首包 0），
   最终用应用精确参数复测 `-ss 20/55.6/62/96` 全部 0.000000 才定论。

### app.js 接入
- `streaming` 条件：`plan==="transcode" && has_video && kind==="video" && Streamer.supported()`；
  失败若 `code !== "NO_MSE"` 才 toast，一律回落原 `prepare_playback`（完整转换 + 缓存副本）路径。
- 新增 `state.streamDuration / streaming / busyUntilPlaying`；新增 `dur()` 统一替代 `video.duration` 读取点。
- 流式路径下 **不调 `video.load()`**（会撕掉 MSE）；`playing` 事件清剩余遮罩。
- 信息面板"播放方式"加后缀"（边转码边播放）"。

### 实测（`/tmp/iplayer-live/slow1080.wmv`，120s 1080p WMV2，741 MB，debug 构建真实窗口）
- **起播 0.73～1.04 秒**（旧方式按 s/内容算需十几分钟；同样内容转 20 s 实测 7 s）。
- 缓冲按需增长（`buf=[0.0-38.4]` 后因 AHEAD=30 停手），编码器被播放节流，无磁盘临时文件。
- 前跳 `96.1`：600ms 内 seeked，新区间 `[96.1-98.0]` 起；到 79.5s 时 `vdur` 收敛到 120.07（finish 收紧）。
- 回跳 `30.0`：落进已有区间直接播，**未重启**（符合预期）。再前跳 `72.1`：新区间正常出现。
- Phase 2：续播 `resume[path]=30` → 打开 0.38s 即 `cur=30.00`；播到 59.78 → 自动接下一文件继续播。
- Phase 3 回归：direct.mp4 / remux.mkv / png / mp3 全部 `err=none`、`busy=false`，无回归。

### 已知取舍（如实告知用户）
- 流式路径拖到极远处是"重开编码器"（~0.5s 恢复），不是零成本。
- 某编码的 MSE MIME 若 WebKit 不支持 → 静默回落"完整转换 + 缓存副本"，不弹错、不影响播放。

## 切文件时立刻停掉转码 —— 转码中切走不再卡住

用户："如果一个视频在转码，切换另一个文件时，立刻停止转码，处理另一个视频的播放，不要卡在这里"。

### 查出的三个真问题
1. **前端竞态（最致命）**：`openFile(A)` 在 `await startStream(A)` 期间切到 B，
   A 的 begin 因 gen 变化抛 ABORTED → A 的 catch 里 `Streamer.stop()` **把刚启动的 B 会话杀了**，
   并把 `state.streaming/streamDuration` 清掉（串到 B 身上）。随后 A 还**继续走 `prepare_playback(A)`**，
   让一个没人看的文件在后台跑完整转码。→ 这就是"卡在这里"。
2. **`prepare_playback` 完全没有取消机制**：切走后 ffmpeg 仍跑满 CPU 直到自然结束；
   且中途失败**遗留半成品文件**，下次 `out.is_file() && len > 1024` 会把它当缓存命中 → 播坏文件。
3. **会话线程泄漏**：`pull()` 在 `rx.recv()` 上永久阻塞，`pump_pipe` 在满载通道的 `tx.send` 上永久阻塞。
   被丢弃的会话没人再消费 → 每次切走泄漏 1 个阻塞线程 + 整个会话（含 ~1 MiB 通道）。

### 修法
- **前端**：`state.openSeq` 票据（不是比对 `file`，否则 A→B→A 会误判）。
  `openFile` 每个 await 之后 `if (stale()) return;`；`openImage` 也 `openSeq++`。
  新增 `releasePlayer()`（= `Streamer.stop()` + `cancelConversion()` + 摘 src）统一"交棒"。
  新增 `cancelConversion()` → `invoke("cancel_playback")`（fire and forget）。
  把 `state.streaming/plan/streamDuration/busyUntilPlaying` 从 `startStream` 里**挪到**新的
  `markStreaming(info)`，只在 `stale()` 通过后调用 —— 否则慢启动会在用户切走后回写全局状态。
  `error` 自愈重试路径同样加 seq 守卫。`openImage` 补 `setBusy(false)`（以前切到图片遮罩会一直留着）。
- **Rust 取消**：`ffmpeg.rs` 新增 `Cancel`（AtomicBool）+ `run_cancellable(...)`；
  `run_with_progress` 变成 `run_cancellable(..., None)` 的包装。
  取消检测在 `-progress` 行循环里做 —— ffmpeg 的 progress 输出是**墙钟节拍**（默认 0.5s 一次），
  所以无需信号/pid，**不到 1 秒内**就停。
  注意本机 Rust 1.99 下 `std::sync::mpsc::SendTimeoutError` 不可用（`no SendTimeoutError in sync::mpsc`），
  改用 `try_send` + `sleep(TICK)` 轮询。
- **`commands.rs`**：`static BUILDING: OnceLock<Mutex<Option<Arc<Cancel>>>>`，
  `claim_build()`（新任务取槽并取消上一个）/ `release_build()`（`Arc::ptr_eq` 确认还是自己的才清）/
  `cancel_playback` 命令（+ `cancel_build()` 供退出时调用）。
  **失败/取消一律 `fs::remove_file(&out)`**（补上 #2 的半成品漏洞）。
  把 cancel 透传 `build_derivative / run_remux / run_transcode / run_audio_transcode`；
  remux 分支里 `if copy_res.is_err() && cancel.is_cancelled()` 直接返回，不再误走"重试转码"。
- **`stream.rs`**：`Session` 加 `stopped: Arc<AtomicBool>`；`kill()` **先置 stopped 再 kill child**；
  `pump_pipe` 改用 `try_send` 轮询（`TICK=150ms`）；`pull` 用 `recv_timeout(TICK)` 轮询检查 stopped。
- **`stream_stop` / `stream_status` 改为 async**（原来 sync 命令在**主线程**执行，
  `kill()` 里的 `child.wait()` 会卡 UI 线程）。`lib.rs` 退出时 `cancel_build() + kill_all()`。
- **`stream.js`**：`stop()` 里补 `restarting = false`（否则上一个会话的跳转守卫会拦住新文件的 seek）。
